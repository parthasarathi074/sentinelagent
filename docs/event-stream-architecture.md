# SentinelAgent Event Streaming and Micro-Batch Architecture

## 1. Purpose

The SentinelAgent event-processing layer collects security events generated by Sentinel Edge instances and provides them to asynchronous analysis components.

The purpose of this layer is to support:

- high-volume inter-agent communication
- parallel event processing
- micro-batch analysis
- behavioral analysis
- temporal analysis
- graph-based relationship analysis
- future collusion detection
- scalable security monitoring

Sentinel Edge performs fast inline security decisions, while deeper analysis is performed asynchronously.

## 3. Kafka Topic

The initial event stream will use a single Kafka topic:

sentinel.events

The first implementation intentionally uses one main topic to keep the architecture simple.

Future versions may separate events into multiple topics such as:

- sentinel.interactions
- sentinel.lifecycle
- sentinel.policy
- sentinel.security

The initial implementation will not introduce this additional complexity.

---

## 4. Partitioning Strategy

Events will initially use `edge_id` as the Kafka partition key.

Example edge identifiers:

- edge-A-B
- edge-A-C
- edge-B-C
- edge-B-D

Using the edge identifier as the partition key helps preserve ordering for events associated with the same logical communication edge while allowing different edges to be processed in parallel.

The system should not create a separate Kafka topic for every agent pair.

The communication edge is treated as a logical concept rather than a separate Kafka topic or necessarily a separate deployed process.

---

## 5. Micro-Batch Processing

The analysis layer will process events in micro-batches instead of performing expensive analysis for every event individually.

A micro-batch can be triggered by either:

1. Event count threshold
2. Maximum time window

Example:

batch_size = 100 events

max_wait = 1 second

Processing occurs when either:

- 100 events have been collected, or
- 1 second has elapsed

This prevents high-volume systems from processing every event individually while also preventing low-volume systems from waiting indefinitely.

The exact batch size and time window will be configurable.

---

## 6. Worker Model

Kafka partitions will allow multiple workers to process events in parallel.

Conceptually:

Kafka
  |
  +--- Partition 0 ---> Worker 1
  |
  +--- Partition 1 ---> Worker 2
  |
  +--- Partition 2 ---> Worker 3
  |
  +--- Partition N ---> Worker N

Increasing the number of partitions and workers can provide horizontal scalability as event volume increases.

Workers will convert incoming events into micro-batches before sending them to the deeper analysis layer.

---

## 7. Failure and Duplicate Handling

The event-processing layer must account for worker failures and duplicate event delivery.

Events should contain a unique `event_id`.

Analysis components should use idempotent processing where possible.

If the same event is received more than once, SentinelAgent should avoid producing duplicate security actions such as:

- duplicate quarantine actions
- duplicate replacement creation
- duplicate alerts
- duplicate state transitions

The system should maintain sufficient processing state to identify events that have already been handled.

---

## 8. Real-Time vs Asynchronous Analysis

SentinelAgent separates security enforcement from expensive analysis.

### Real-time Sentinel Edge responsibilities

Sentinel Edge performs fast checks such as:

- source identity validation
- target identity validation
- permission validation
- target status validation
- policy checks
- immediate communication decisions

Possible decisions include:

- ALLOW
- DENY
- RESTRICT
- THROTTLE

### Asynchronous analysis responsibilities

The asynchronous processing layer performs more expensive analysis such as:

- behavioral analysis
- temporal analysis
- communication-frequency analysis
- relationship/graph analysis
- coordinated behavior analysis
- collusion detection
- risk scoring

This separation prevents expensive analysis from unnecessarily increasing communication latency.

---

## 9. Future Collusion Analysis

Individual interactions may appear normal when viewed independently.

For example:

A -> B
B -> C
A -> C

A deeper analysis may identify relationships that are suspicious when considered together.

The future Collusion Engine will analyze groups of events across:

- agents
- runtimes
- communication edges
- time windows
- resources
- actions
- permissions

The system may eventually construct an interaction graph such as:

        A
       / \
      B---C
       \ /
        D

This graph can be combined with temporal and behavioral information to calculate a collusion risk.

The exact detection algorithm will be designed in a later project step.

---

## 10. Scalability Considerations

The architecture is designed so that event collection and analysis can scale independently.

The Sentinel Edge should remain lightweight because it is part of the communication path.

Heavy analysis should occur asynchronously.

Kafka partitions provide parallelism for event consumption.

Micro-batching reduces the overhead of repeatedly performing expensive analysis on individual events.

The architecture should support increasing:

- number of agents
- number of communication edges
- event rate
- number of analysis workers

without requiring the entire pipeline to stop.

---

## 11. Design Decisions

The following decisions are established for the initial SentinelAgent architecture:

| Area | Decision |
|------|----------|
| Event stream | Kafka |
| Initial topic | sentinel.events |
| Partition key | edge_id |
| Processing model | Parallel workers |
| Analysis model | Micro-batch |
| Batch trigger | Event count OR time |
| Inline analysis | Lightweight security checks |
| Deep analysis | Asynchronous |
| Event identity | Unique event_id |
| Duplicate handling | Idempotent processing |
| Raw payload handling | Avoid unnecessary sensitive payloads |
| Agent quarantine | Persistent |
| Agent replacement | New runtime identity and credentials |

These decisions provide the foundation for the event-processing and analysis layers of SentinelAgent.
